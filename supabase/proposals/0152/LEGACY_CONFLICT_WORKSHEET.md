# Legacy-conflict resolution worksheet (Proposal 0152) -- NO production data, NO query has been run

Purpose: one row per kind of unresolved invoice / payment / factoring / recipient / carrier-ownership conflict the 0130-0152 chain can surface, with the **read-only** query that finds the affected records, the **human business decision** that is required, and the **permitted** resolutions. The queries are in `production_package/legacy_conflict_queries.sql` (Q01-Q16, one statement each, statically proven read-only by `discovery_guard.py check-files`). They have been syntax-checked and exercised only on a disposable local database seeded with **synthetic** rows in a model of the columns used; they have **not** been run on the real schema or on production, and must be re-validated on a disposable copy of the migrated schema before the window. Their results are confidential business data: never paste them into chat, tickets or the repository.

## Global rules (apply to every row; violations are STOP conditions)
1. **Never guess.** A carrier is assigned to a record only if a named person with authority decides it, from documents that prove it (rate confirmation, dispatch record, carrier contract, remittance/NOA), and the evidence is recorded.
2. **No mass assignment.** No `UPDATE ... SET carrier_id = ...` over a set, no "set all to the only carrier", no default fills. One record, one decision, one recorded evidence reference.
3. **No silent deletion.** Nothing is deleted or archived to make a query return zero. A record is closed only through a sanctioned path with a recorded reason (below); exception rows are retained.
4. **Historical financial records are not rewritten.** Invoices, payments, factored-invoice snapshots and numeric fields are never edited to resolve ownership; a wrong future routing is corrected by a new configuration (new relationship, policy, re-issued invoice), never by repointing history (`0138:537-540`).
5. **Sanctioned mechanisms only:** `set_carrier_factoring_policy` (0139), `set_default_factoring_relationship` (0138), `approve_factoring_relationship_noa` (0140), creating a NEW relationship (owner/admin, 0140) and `deactivate_factoring_relationship` (0141), `review_legacy_invoice_carrier_migration` (0142/0152) with a written `p_resolution`, `reassign_dispatch_resources` (0135), the first-dispatch claim of an eligible load (0132), and status changes on `unresolved_carrier_records` by an owner/admin. No direct table UPDATE of `carrier_id`/`is_default` (revoked, `0138:517-533`).
6. **Decision record.** Each resolved row keeps: query id, record id, date, decider's name and role, evidence reference (document id/number, not contents), chosen resolution, second reviewer. Kept outside the repository.
7. **Gate.** The runbook requires every row below to be either **confirmed empty** by its query or **explicitly resolved/accepted in writing by the Owner** before the maintenance window. `PRE` queries are run at production discovery (0129 boundary); `POST` queries only inside the window after the named migration.

## Factoring of legacy invoices is EXCLUDED (Owner decisions D-08a/D-08b)
Legacy `invoices` are never submitted to a factor (proposal 0156 is superseded). Rows C01-C04 and C09-C11 therefore feed the **gate of proposal 0157** (D-08i): the operator cannot enable carrier-invoice factoring while a 0155 review is pending or a factoring exception (`factoring_relationship`, `factored_invoice`) is open. Legacy invoices that still need factoring must be **reissued as carrier invoices** (C09: `missing_carrier_evidence`, `conflicting_*` and `safely_identifiable_legacy` invoices are the population); the app has no UI for that workflow yet.
