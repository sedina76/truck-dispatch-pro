# Deployment runbook: migrations 0130–0146

Production readiness is **NOT YET EVALUATED** until `PRODUCTION_PREFLIGHT_0130_0146_READONLY.sql` is run against production and its output is reviewed. The audit never changes the database.

Migration 0137 classifies every relationship using exactly two ordered rules. An organization with exactly one carrier resolves to that carrier regardless of evidence. Otherwise, each factored invoice contributes `coalesce(dispatch.carrier_id, load.carrier_id)`; one distinct non-null candidate resolves as `multi_carrier_org_provable`, zero candidates becomes `unresolved_no_evidence`, and two or more become `unresolved_multiple`. A single invoice whose non-null dispatch and load carriers disagree is a structural abort. The migration applies no dispatch-status filter, so cancelled dispatch evidence is not excluded. At its pre-apply boundary every `factoring_relationships.carrier_id` must be null and the provenance table must be absent; consequently a pre-existing assignment is a rerun/precondition failure, not a fifth resolution class.

NOA document states are classified separately. A non-null `noa_document_id` without a document row is `FACTOR_NOA_DOCUMENT_DANGLING` (BLOCKER), because the foreign key was bypassed or damaged. An existing document from another organization is `FACTOR_NOA_DOCUMENT_ORG_MISMATCH` (BLOCKER), because the organization guard normally prevents that cross-tenant reference. An existing same-organization document that is merely unverified remains `FACTOR_NOA_DOCUMENT` (WARNING): it is incomplete readiness and issuance already fails closed. A null document ID is valid when approved template text supplies the NOA, as migration 0140 explicitly permits.

The 0141 integration rules require `is_active` exactly when status is `ready`, allow at most one active integration per relationship, and guard organization, carrier, relationship, and factoring-company identity on both INSERT and UPDATE. `FACTOR_INTEGRATION_CROSS_ORG` is limited to a tenant mismatch against the integration's carrier, relationship, integration company, or relationship company. Within one organization, `FACTOR_INTEGRATION_CARRIER_MISMATCH` covers a carrier-only disagreement, `FACTOR_INTEGRATION_COMPANY_MISMATCH` covers a company-only disagreement, and `FACTOR_INTEGRATION_RELATIONSHIP_MISMATCH` covers a missing relationship or one incompatible with both recorded carrier and company. These mutually scoped identity findings leave a correctly linked nondefault relationship to `FACTOR_INTEGRATION_READY_NONDEFAULT`. The combined cross-organization plus carrier-only fixture intentionally emits both CROSS_ORG and CARRIER_MISMATCH because it contains two independent corruptions.

A ready integration also requires a factored carrier, an active default relationship, and an active factoring company. The normal `carrier_factoring_integrations_guard_org` trigger calls `guard_carrier_factoring_integration_org()` and rejects all four malformed identity chains. Each disposable fixture uses `session_replication_role=replica` only inside its isolated clone to bypass that INSERT/UPDATE trigger and foreign-key enforcement, runs the read-only audit, and is destroyed by the harness cleanup; no migration source is changed. The audit reports BLOCKER findings without exposing identifiers, names, destinations, or secret references. Legitimate inactive lifecycle states remain informational, while a complete ready integration is accepted.

Legacy `public.invoices` remain the pre-carrier legal-document model. Their installed status enum is exactly `draft`, `sent`, `viewed`, `partially_paid`, `paid`, `overdue`, `void`, and `disputed`; the table has no durable `carrier_id`. The 0142 classifier derives carrier evidence only from the invoice's `load_id` and the load's `carrier_id`/`carrier_resolution`, and derives the recipient only from the invoice's broker/customer pair. Its precedence is exact: void; paid or partial amount; any `factored_invoices` row; both recipients; neither recipient; missing/unresolved load carrier; conflicting load carrier; safely identifiable legacy. It does not inspect invoice `dispatch_id`, dispatch status, current carrier-party eligibility, or payment rows.

`public.payments` is the authoritative legacy payment ledger, including the later posted/voided reversal state, while `public.factored_invoices` is the authoritative evidence that factoring activity exists regardless of terminal status. These histories are inventory and stop conditions for automatic handling; they are never copied into the separate carrier-invoice model by this audit. The audit calls neither `scan_legacy_invoices_for_carrier_migration()` nor `review_legacy_invoice_carrier_migration()`. Review rows remain unique per legacy invoice, client read-only, organization-scoped by RLS, and mutable only through the owner/admin RPC that derives reviewer identity and time on the server.

One authoritative defect is recorded for later migration work, and remains a release **BLOCKER**: 0142 tests `loads.carrier_resolution = 'conflicting'`, but the 0132 CHECK permits only `resolved`, `backfilled`, or `unresolved`. The normal 0133 conflict outcome is stored as `unresolved`, so the classifier's `conflicting_carrier_evidence` branch is unreachable in a constraint-valid database and is preceded by the missing/unresolved branch. The audit preserves exact equivalence with the installed function. Its conflict-bucket fixture deliberately drops the CHECK only in an isolated clone to prove the dead branch and classify a constraint-bypassed production row as a blocker; that bypassed test proves the branch's own logic is correct, never that the branch is reachable in a real, constraint-valid production database -- it is not. This package does not alter the migration, and this audit phase (Phase 3C.0E) does not alter it either. A corrective migration (not 0147, not created in this phase) is required before production rollout. Until that corrective migration lands, existing `unresolved` records must NOT be automatically reclassified as `conflicting` -- that would require exactly the same load/dispatch-carrier-disagreement evidence 0133 already had available and chose not to encode as `conflicting`, and silently reinterpreting historical `unresolved` rows is the same class of destructive reinterpretation this whole package refuses to perform elsewhere (Section J's legacy-invoice policy, Section E's immutable snapshots). The overall deployment decision remains **BLOCKED** while this defect is unresolved, independent of every other finding in this file.

The eight-row disposable comparison evaluates the audit CASE and `classify_legacy_invoice_for_carrier_migration(uuid)` row-for-row, including carrier and recipient labels, and requires zero mismatches. Five overlapping-condition fixtures lock the documented precedence. The complete 70-scenario legacy matrix covers recipient and carrier integrity, payment/factoring history, review authorization/integrity, clean-0129 and post-0146 no-conversion behavior, comparison failure guards, privacy markers, and before/after hashes. Output contains only stable findings, classifications, counts, severities, decisions, and remediation; invoice notes, billing fields, payment references, factoring references, and review text are suppressed.

The 0139–0141 field rules distinguish stored configuration from readiness. `submission_method` and `effective_from` are always non-null. API rows structurally require a non-null `secret_reference`; 0141 also constrains it to an opaque URI shape. API readiness additionally requires `provider = factoring_api` and a nonblank `external_account_identifier`. `submission_destination` is not an API-readiness requirement: it is required for secure-email and portal-manual rows, with the secure-email constraint also validating address shape. `approved_by` and `approved_at` are required together only while `is_active` is true, and 0141 ties `is_active` exactly to `configuration_status = ready`. `effective_to` may be stored when it is not before `effective_from`, but any finite value blocks ready status because no scheduler performs expiry. The dependency matrix keeps incomplete ordinary configurations inactive and reports warnings; persisted ready/active approval, date, NOA, policy, or default contradictions are blockers.

Runtime role tests preserve 0141's intended disclosure boundary. Same-organization owners and admins can read the base integration row, including its opaque `secret_reference` pointer and non-secret external-account display value, but the pointer is never the credential itself. Accountant and dispatcher roles receive only the status and readiness RPC results; driver, viewer, cross-organization, anonymous, invalid-profile, and `auth.uid() = null` callers receive no client-authorized configuration. `get_carrier_factoring_integration_status(uuid)` intentionally returns the external-account display identifier to the four authorized operational roles, while omitting `secret_reference`; `classify_carrier_factoring_readiness(uuid,uuid,uuid)` returns only readiness classification and identifiers. Runtime recursive checks reject credential/secret/password/token/private-key keys and the seeded opaque-pointer value. All authenticated direct INSERT, UPDATE, and DELETE privileges on the integration table remain revoked. Owner/admin lifecycle probes are transactionally rolled back, and row, grant, policy, and function-definition hashes remain unchanged.

## Authorization and preparation

The deployment requires the service owner, an authorized production database operator, and a second reviewer familiar with carrier billing. Confirm a restorable backup or point-in-time recovery point and record its timestamp and restoration procedure. Use a maintenance window sized for sequential verification and backfill review. Record the application Git commit, database migration-history boundary, database identifier, operator, reviewer, and start time in the deployment evidence folder.

Fail closed all server paths that can create or issue carrier invoices for the whole window. Confirm that background jobs, API workers, and administrative paths cannot issue them. Do not rely on hiding UI controls.

The supported execution environment is **psql**. The SQL file uses `\gexec` to run SELECT-only queries for catalog-confirmed optional tables; it is not compatible with Supabase SQL Editor. Use a production connection supplied through the operator's approved secret-management method, then run `psql -X -v ON_ERROR_STOP=1 -f supabase/PRODUCTION_PREFLIGHT_0130_0146_READONLY.sql > preflight-0130-0146.txt 2>&1`. Verify the psql exit status before reading the decision. Restrict the output file to authorized personnel; it contains counts and schema findings, although it intentionally omits raw document and secret values. Review every BLOCKER and WARNING. Proceed only if the computed decision is `READY` or an owner and reviewer accept every documented warning. `BLOCKED` and `SCHEMA_STATE_UNKNOWN` are stop decisions. Proceeding also requires `audit_coverage_status = COMPLETE`; a `PARTIAL`/`INCOMPLETE` coverage status is its own stop condition regardless of the computed decision, because an incomplete audit cannot certify that no further BLOCKER remains undiscovered.

Never type the production password or full connection string directly on the command line, and never export it in a way a shell history file or process listing (`ps`, `history`) would capture it in cleartext -- supply it only through the operator's approved secret-management method (for example a `.pgpass` entry, an interactively-prompted password, or a short-lived environment variable set in a non-logged subshell and unset immediately after use), and disable shell history for that session if the method cannot avoid a command-line credential. The production connection must use TLS (`sslmode=require` or stricter, per Supabase's connection guidance); do not connect over an unencrypted transport. Every retained artifact -- the preflight/post-apply output files, the evidence folder itself, and any exported audit result -- must be created with restrictive filesystem permissions (for example `chmod 600` on files and `chmod 700` on the containing directory) and stored only in the approved restricted evidence location; never paste production data, audit output, row counts, or finding details into a public ticket, chat channel, shared log, or any system without equivalent access restriction.

### Preserved corrective-migration backlog (7 BLOCKERs + 1 WARNING)

This is the authoritative, consolidated list of every release-blocking defect this audit package has found and permanently documented without fixing. Each is tracked individually -- none is downgraded, combined with another, marked resolved, or described as theoretical -- and each remains open as of this package:

1. **BLOCKER** -- `LEGACY_CLASS_CARRIER_CONFLICT`: migration 0142 tests `loads.carrier_resolution = 'conflicting'`, a value the 0132 CHECK constraint never permits in a constraint-valid database, making that classifier branch unreachable in production (see the "One authoritative defect is recorded..." paragraph above for the full analysis).
2. **BLOCKER** -- `FIN_CARRIER_INVOICES_AUTH_INSERT`: `carrier_invoices` grants `authenticated` a direct table-level `INSERT`, letting an owner/admin/accountant (or a dispatcher while `issuance_status = 'draft'`) forge an invoice row entirely outside `issue_carrier_invoice()`.
3. **BLOCKER** -- `FIN_CARRIER_INVOICES_AUTH_DELETE`: `carrier_invoices` grants `authenticated` a direct table-level `DELETE`; confirmed scope is a **draft or ready-for-issue** invoice only, since `guard_carrier_invoice_delete()` already rejects deleting an issued or voided one.
4. **BLOCKER** -- PUBLIC/anon `EXECUTE` on `update_carrier_invoice_draft(uuid,jsonb,timestamptz,text,text)` (exact installed signature).
5. **BLOCKER** -- PUBLIC/anon `EXECUTE` on `review_legacy_invoice_carrier_migration(uuid,text,text,timestamptz,text)` (exact installed signature).
6. **BLOCKER** -- PUBLIC/anon `EXECUTE` on `scan_legacy_invoices_for_carrier_migration()` (exact installed signature). Items 4-6 are jointly asserted by `FUNC_CLIENT_RPC_KNOWN_GAPS`, whose count sums a per-signature check across these three named functions -- each is independently identified by exact signature in that finding's own source and remediation text, not merged into one generic description.
7. **BLOCKER** -- `FUNC_NULL_IDENTITY_AUTH_BYPASS`: a null-identity caller (anon, or authenticated with no profile row) of `scan_legacy_invoices_for_carrier_migration()` silently bypasses its intended owner/admin-only check, because `has_role()` returns NULL rather than false and PL/pgSQL's `IF NOT NULL` is not true.
8. **WARNING** -- `FUNC_RAISE_LEAKS_CONTEXT`: five 0130-0135 RPCs (`activate_carrier_party`, `approve_trailer_ownership_scope`, `transition_dispatch_status`, `reassign_dispatch_resources`, `record_unresolved_carrier_record`) raise a raw PL/pgSQL exception for an ordinary error, leaking function name and line number via CONTEXT instead of the structured `{success:false,...}` result later RPCs use.

## Sequential procedure

This section documents the procedure for a future, separately authorized deployment window; publishing this runbook is not an instruction to apply 0130-0146 now, and none of them are applied by this audit package. Migrations 0130 through 0146 must be applied strictly in ascending numeric order -- never skipped, reordered, or batched out of sequence -- because each migration's preflight assumes the exact boundary left by the previous one. Already-applied migrations must never be rerun. For each unapplied row below, run its preflight at that exact boundary, review every row, apply the migration once, immediately run its post-apply verifier, preserve all three outputs, and stop on any SQL error or failed check. Do not begin this sequence while the consolidated preflight reports `BLOCKED`, `SCHEMA_STATE_UNKNOWN`, or an incomplete `audit_coverage_status`; as of this package, seven release BLOCKERs remain open (see "Preserved corrective-migration backlog" above), so the sequence below is not yet authorized to start. The corrective migration required to resolve those BLOCKERs is future work, referred to here as migration 0147; it does not exist yet and is not part of this deployment or this audit package. Only after 0147 is designed, reviewed, applied, and re-audited as `READY` (or `READY_WITH_WARNINGS` with every warning explicitly accepted) may this sequential procedure begin. Application deployment (enabling any multi-carrier invoice UI or issuance path) is its own separate approval and must not occur until the database side of this sequence is complete and re-audited.

Rollback scripts and repair scripts are manual emergency tools, never routine deployment steps. Read each rollback's refusal checks first and roll back dependents in reverse order, 0146 toward 0130. Never force a rollback past invoices, snapshots, payments, provenance, or other business records. Prefer roll-forward when a later migration has created durable business data, when rollback refusal conditions apply, or when a narrowly reviewed corrective change preserves history more safely. Once any of those refusal conditions is reached, the only paths are roll-forward or a narrowly reviewed, manually authored corrective change; there is no guaranteed way back to the pre-0130 state.

## Phase 3C.0E.3: payment ledger, financial RLS, and end-to-end RPC closure

### Authoritative 0146 payment contract (re-inspected directly from `record_carrier_invoice_payment`/`void_carrier_invoice_payment`)

Allowed invoice document types: `carrier_freight_invoice`, `dispatch_service_invoice` (0142). Allowed issuance states for a NEW payment: `issued` only (`draft`/`ready_for_issue` and `voided` both return `INVALID_STATE`, with different message text but the identical code). Carrier factoring modes relevant here: a payment is accepted only when the invoice's own validated version-2 snapshot reports `factoring.mode <> 'factored'`; `factored` yields `FACTORED_INVOICE_PAYMENT_REQUIRES_FUNDING_WORKFLOW`. Payment lifecycle/status: `posted` → `voided` only (never reactivated, never deleted). Posting metadata: `recorded_by` = `auth.uid()`, `created_at`/`updated_at` server-derived. Void metadata: `voided_by` = `auth.uid()`, `voided_at` = `now()`, `void_reason` = the RPC's own required, non-blank `p_reason` parameter. Amount/currency rules: amount must be `> 0`; currency is always server-derived from the invoice row (never client-supplied), with a cross-table trigger backstop (`guard_carrier_invoice_payment_currency`) making a mismatch structurally unreachable via the RPC. Balance rollup: `amount_paid` is recomputed from the **sum of currently-posted payments** (not incrementally trusted), rejecting an insert that would exceed `total_amount` (`OVERPAYMENT`). Payment-status derivation: `unpaid` (0) / `partially_paid` (0 < paid < total) / `paid` (paid ≥ total) — identical formula in both `record_` and `void_`. Idempotency scope: `(organization_id, operation, idempotency_key)`, fingerprint = SHA-256 of a canonical, fully-keyed payload covering every request field including `expected_updated_at`; a same-key/different-fingerprint replay returns `IDEMPOTENCY_KEY_REUSED`, never applies a mixed result. Authorization roles: `owner`/`admin`/`accountant` only, for both record and void; every other role (including `dispatcher`) is `FORBIDDEN`; `auth.uid() IS NULL` (unauthenticated, including `service_role`, which has no `auth.uid()` of its own) is `FORBIDDEN` before any role check. Lock order: advisory lock on `(org, operation, idempotency_key)` → invoice row `FOR UPDATE` → (void only: provisional unlocked read of the payment's own immutable `carrier_invoice_id`, then the invoice, then the payment row `FOR UPDATE` with an organization filter) → every other posted payment for the same invoice, ascending id, `FOR UPDATE`. Immutable-snapshot dependency: `record_carrier_invoice_payment()` calls the single canonical `carrier_invoice_payment_snapshot_problem()` (0146) before ever inserting a payment row; a non-version-2 snapshot fails closed with `SNAPSHOT_VERSION_UNSUPPORTED`, an internally-inconsistent version-2 snapshot fails closed with `SNAPSHOT_INTEGRITY_ERROR` -- neither ever returns snapshot content. None of this imports any assumption from the legacy `public.payments` table; the contract above comes entirely from 0146's own installed function bodies.

### Investigative note: a suspected platform-wide missing-RLS blocker was ruled out

While building Section B's inventory, a live query against this phase's disposable database showed `relrowsecurity = false` for `carriers`, `loads`, `dispatches`, `documents`, `invoices`, `payments`, `organizations`, `profiles`, and `integration_settings` -- and a direct behavioral test confirmed a same-org owner's `select count(*) from public.carriers` returned a row belonging to a *different* organization. This looked like it could be the single most severe finding in the entire audit series: platform-wide, cross-tenant data exposure on foundational tables, pre-dating 0130.

It was **not** a real defect. Exhaustive, direct inspection of every migration 0001-0146 (not merely a grep for the literal string `"enable row level security"`, which is insufficient here) found that `0010_rls_policies.sql` enables RLS for these exact tables via **dynamic SQL** -- `execute format('alter table public.%I enable row level security;', t)` inside `do $$ ... foreach t in array standard_tables ... $$` blocks -- so the table name never appears as a literal string next to "enable row level security" in the migration source. `factored_invoices`/`factoring_events` are separately covered by `0071_factoring_schema.sql`. A second, independent grep across every one of the ~60 migrations that mention RLS anywhere, filtered to the exact bare table names of concern, confirmed zero gaps. The root cause of the *false positive* was `TEST_SUPPORT_0130_0133_schema.sql` (a pre-existing, unmodified test-support file, per its own header comment: "RLS mirrors 0010's blanket grant") -- this disposable-database bootstrap stub reproduces 0010's raw table-level `grant ... to authenticated` but only reproduces the *RLS-enablement* half of 0010 for `trailers`, not for the other tables in 0010's own dynamic loops. Testing against a database built from this stub therefore showed the stub's own simplification, not production's real behavior. This is recorded here, not corrected in the (unmodified) test-support file, so a future audit does not have to re-derive this conclusion from scratch: **`carriers`, `loads`, `dispatches`, `documents`, `invoices`, `payments`, `factored_invoices`, and `factoring_events` all have real, working RLS in the actual migration history** (0010/0071); the stub used to build disposable pre-0130 fixtures simply does not reproduce that specific mechanism for anything but `trailers`. Grant/policy *behavior* (as opposed to bare RLS enablement) for these pre-existing tables remains genuinely untested by this audit series and is recorded as such in manifest rows 97/101/103/104, not conflated with this ruled-out RLS-enablement concern (row 100).

### THREE GENUINE DEFECTS FOUND -- one already known, two newly discovered siblings

1. **`update_carrier_invoice_draft`** (already known, Phase 3C.0E.3) -- anon/PUBLIC EXECUTE never revoked. Behaviorally safe for a pure-anon caller (an early `current_org_id() IS NULL` check returns a clean `NO_ORGANIZATION` result before any role check).
2. **`review_legacy_invoice_carrier_migration`** (0142) -- **NEWLY DISCOVERED sibling**: the exact same missing-revoke pattern (0142 grants EXECUTE to authenticated for this function but never adds the accompanying `revoke all ... from public, anon` that its own sibling `classify_legacy_invoice_for_carrier_migration` correctly receives two lines after its own creation, in the SAME migration). Behaviorally safe for the same reason as (1): an early `current_org_id() IS NULL` check.
3. **`scan_legacy_invoices_for_carrier_migration`** (0142) -- **NEWLY DISCOVERED sibling** with the same missing-revoke gap, but **NOT behaviorally safe**: its authorization check (`if not public.has_role(...) then raise exception ... end if;`) is the function's literal first statement, with no prior null-identity guard. `has_role()`'s own body (`select current_role() = any(p_roles)`) returns SQL NULL -- not `false` -- when the caller has no resolvable profile row (true for anon, or an authenticated session with no profile), because `NULL = any(array)` is NULL. PL/pgSQL's `IF NOT (NULL) THEN` does not enter the THEN branch (NULL is not TRUE), so the intended `42501 FORBIDDEN` exception is **silently skipped**, and execution falls through to the function's own org-scoped loop, which then matches zero rows (`current_org_id()` is also NULL) and returns `0` -- a misleading "nothing to process" success instead of a clear authorization error. **Confirmed directly**: `set role anon; select public.scan_legacy_invoices_for_carrier_migration();` returns `0`, not an error. No real tenant data is read or written in practice (the org-scoping is itself NULL-safe), but the intended fail-closed contract is violated -- this is a real, previously-undocumented BLOCKER (`FUNC_NULL_IDENTITY_AUTH_BYPASS`), distinct in *kind* from the missing-revoke gaps: even if EXECUTE were correctly revoked from anon today, this exact code pattern would silently misbehave for ANY future caller reachable with a null identity. A genuine remediation was verified: redefining the function with `if auth.uid() is null or not coalesce(public.has_role(...), false) then raise exception ... end if;` (the same defensive pattern the codebase already knows -- Phase 3C.0F.1's own `PLAT_WRITE_GRANT_UNDOCUMENTED` documentation established the convention of checking identity before role) makes the anon call correctly raise `FORBIDDEN` instead of returning `0` (`func_null_identity_auth_bypass_fix_verified`).

None of these three are fixed in this phase; migrations are not modified.

### Section G: caller-supplied identity

A structural catalog scan (`identity_param_scan`) confirms **zero** of the 50 non-trigger functions accept a `created_by`/`approved_by`/`reviewed_by`/`issued_by`/`posted_by`/`voided_by`/`recorded_by`/`actor_id`/`user_id` parameter -- every identity field in every RPC in this range is always server-derived from `auth.uid()`, with no exception. `record_unresolved_carrier_record` is the one function that DOES accept an explicit `p_organization_id`; its body validates this against `current_org_id()` for any interactive (non-null `auth.uid()`) caller, rejecting a mismatch with `42501 cross-organization write rejected` (confirmed behaviorally). Its documented "trust a null-`auth.uid()` caller" branch (intended for migration/backfill contexts, e.g. 0133's own backfill) is confirmed **unreachable by any live client role**: `anon` lacks EXECUTE entirely, and `service_role` in this schema also lacks EXECUTE and holds neither superuser nor `BYPASSRLS` -- there is no path by which an external actor reaches that branch. `exact_identity_forgery_matrix` additionally exercises 4 representative behavioral forgery attempts (cross-org organization_id, cross-org carrier_id, same-org role-unauthorized action, null auth context) -- all fail closed.

### Section H: dynamic SQL and injection

Exhaustive grep confirms exactly 3 `EXECUTE format(...)`/`EXECUTE '...'` usages across all of 0130-0146, and all 3 are migration-time-only `DO` blocks (never inside a client-callable RPC body): a hardcoded literal table-name array (0131), a `pg_attribute`-derived column name (0141), and a `format(...,%L,...)` literal-quoted `COMMENT ON COLUMN` (0133) -- none ever incorporates a request parameter, JSON-patch key, or any other caller-controlled value. A live injection attempt through `set_carrier_factoring_policy`'s `p_reason`/`p_idempotency_key` parameters (SQL-metacharacter-laden strings including an embedded `DROP TABLE`) was processed as inert text; the target table was confirmed to still exist afterward.

### Section I: structured-error non-disclosure

`exact_structured_error_matrix` distinguishes two error-handling conventions present in this migration range, discovered while investigating this section: RPCs from **0138 onward** (factoring integration/policy, carrier-invoice/payment, dispatch-service agreements) consistently return a clean `{"success": false, "code": "...", "message": "..."}` jsonb payload for every ordinary/anticipated error condition, confirmed directly (`activate_carrier_factoring_integration`, `create_carrier_dispatch_service_agreement`, `issue_carrier_invoice`). Five **earlier** RPCs (0130-0135: `activate_carrier_party`, `approve_trailer_ownership_scope`, `transition_dispatch_status`, `reassign_dispatch_resources`, `record_unresolved_carrier_record`) instead `RAISE EXCEPTION` for these same ordinary conditions (not-found, forbidden, cross-organization) -- confirmed directly by forcing each condition. The raised message text itself never includes a SQLSTATE code, constraint name, or table/relation name (confirmed: no occurrence of `sqlstate`/`detail:`/`hint:`/`constraint "`/`relation "` in any forced-error output across either convention), but PostgreSQL's own `CONTEXT` block necessarily reports the internal function name and the raising statement's line number for any raised exception -- information the newer convention never exposes at all, since it never raises for these cases. New finding `FUNC_RAISE_LEAKS_CONTEXT` (WARNING; count 5) reports this precisely, distinguishing a genuine "raises for ordinary input" defect from a harmless text match against `issue_carrier_invoice`'s own legitimate defensive assertions (which also contain the string "raise exception" but never fire for ordinary input).

### Reconstructing a genuinely faithful pre-0130-plus-0146 test environment

### A critical near-miss: two investigations that could have produced a false positive

**Investigation 1 -- the single most severe possible defect, found and then found-already-fixed.** While reviewing `profiles`' policies, `profiles_update_self`'s own text (`for update using (id = auth.uid()) with check (id = auth.uid())`) contains no restriction on which *columns* a user may change on their own row. A direct test against the reconstructed database, built from only `TEST_SUPPORT_0130_0133_schema.sql` + `0010`, confirmed a same-org **viewer** (the lowest-privilege role) could `UPDATE public.profiles SET organization_id = '<any other org>', role = 'owner' WHERE id = auth.uid()` and succeed -- instantly becoming the owner of any organization, with `current_org_id()`/`current_role()` (which every RLS policy in the entire platform trusts) reflecting the forged values, granting real read access to that organization's carriers, loads, and by extension everything else. This would have been the most severe finding in this entire audit series.

Before reporting it, the full 0001-0129 migration range was searched for any later corrective migration -- and `migrations/0012_profile_privilege_guard.sql` exists, with a header that verbatim describes this exact gap and closes it with a `protect_profile_privileged_columns()` guard trigger (rejecting any `organization_id`/`role` change unless the caller is already owner/admin of the row's pre-update organization, or a sanctioned SECURITY DEFINER onboarding RPC has set a session-local bypass flag). Applying 0012 for real and re-running the identical exploit attempt produced `insufficient_privilege: only owner/admin may change organization_id or role` -- correctly blocked. **This is a real, documented, already-fixed historical gap, not a live defect** -- confirmed via the migration's own source, not assumed. Both states (blocked with 0012, exploitable without it) are proven directly and permanently as `PRE0130_PROFILE_PRIVILEGE_GUARD_MISSING`.

**Investigation 2 -- migrations marked "PROPOSED ONLY -- NOT APPLIED" that were, in fact, applied.** Migration `0066_financial_rls_hardening.sql` (which narrows legacy `invoices`/`settlements`/`payments`/etc. SELECT access from "any org member" to owner/admin/dispatcher/accountant, excluding driver/viewer) carries a header stating "PROPOSED ONLY -- NOT APPLIED," as do roughly twenty consecutive migrations from 0066 through 0084. Taking this literally would mean these tables' SELECT policy is still 0010's original, broader version in production today. Cross-referencing downstream evidence resolved this: migration `0129_atomic_dispatch_lifecycle.sql` (unambiguously live, since 0130 depends on it) itself raises a hard precondition-failure exception if `public.dispatch_financials` (created by 0067) is missing, and `0145_carrier_dispatch_service_agreements_and_issuance.sql` does the same for `public.load_financials` (also 0067) -- both treat 0067 as a live, required precondition, not a draft. `TEST_SUPPORT_0130_0133_schema.sql`'s own header separately states its `loads`/`dispatches` shape is "post-0069/0115." **The "PROPOSED ONLY" header text reflects each file's original drafting stage, not its final, eventually-applied status** -- these migrations were approved and applied without the stale caution banner being edited out (a defensible practice: migrations, once applied, are not normally re-edited). 0066 was applied to the test environment on this basis, and `PRE0130_FINANCIAL_SELECT_ROLE_TOO_BROAD` asserts the narrower policy is in place.

Both investigations are recorded here specifically so a future audit does not have to re-derive either conclusion from scratch.
